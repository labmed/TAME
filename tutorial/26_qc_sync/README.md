# 26. 계속 쌓이는 파일 처리: `tametools sync` 와 Westgard QC

정도관리(QC)처럼 **같은 엑셀 파일에 행이 하루씩 쌓이는** 자료를 위한 흐름입니다.
파일은 셋뿐이고 이름이 바뀌지 않습니다.

| 파일 | 누가 고치나 | 내용 |
|---|---|---|
| `qc_chem_daily.xlsx` | 검사실(사람) | 원본. 매일 아래에 행을 추가 |
| `qc_chem.tame` | 설정은 사람, 나머지는 `sync` | 설정(META) + 원본 스냅숏(DATA) + 동기화 이력 + 조치·검토 기록 |
| `qc_chem_result.tame` | `sync` | Westgard 판정 결과(표). 매번 같은 파일을 갱신 |
| `qc_chem_report.html` | `sync` | 관리도(Levey-Jennings)가 들어간 보고서. 매번 같은 파일을 갱신 |

방향은 그대로 원본 → 프로젝트 → 결과 한쪽이지만, 실행할 때마다 새 파일을 만들지 않고
**무엇이 언제 바뀌었는지를 파일 이름이 아니라 파일 안의 이력**에 남깁니다.

## 바로 실행

```sh
python tutorial/26_qc_sync/run_demo.py
```

`outputs/` 를 새로 만들고 아래 순서로 실행해 보고 내용을 출력합니다. 자료는 합성 관리물질 값이며 환자 자료가 아닙니다.

1. 20일치(40행) 엑셀을 처음 동기화 → 결과 120행(검사 3종 × 40측정)
2. 바로 다시 실행 → `변경 없음`, 어떤 파일도 쓰지 않음
3. **다음날 Level 1 측정 1행 추가** → 원본 `추가 1`, 결과 `새 결과 3`
   - Glucose 95 (z=+2.5, 전날도 +2.5) → `2_2s` 거부
   - Creatinine 0.92 (z=+0.67, 10일 연속 평균 위) → `10x` 거부
   - ALT 36 (z=+2.67, 단독) → `1_2s` 경고만
4. 같은 run 의 Level 2 측정 1행 추가 → `새 결과 3 · 변경 2`
   (ALT 가 +2.67 / −2.5 로 갈려 `R_4s`, 이미 보고한 Level 1 ALT 행이 경고 → 거부로 변경)
5. 이미 동기화한 값을 엑셀에서 정정 → 저장하지 않고 중단, `--accept-changes` 로 확인 후 반영
6. `--history` 로 프로젝트 안의 이력 확인

## 매일 쓰는 명령

```sh
tametools sync qc_chem.tame                    # 원본을 다시 읽어 프로젝트와 결과를 갱신
tametools sync qc_chem.tame --check            # 무엇이 바뀔지만 확인(파일을 쓰지 않음)
tametools sync qc_chem.tame --accept-changes   # 이미 동기화한 행의 수정/삭제를 정정으로 인정
tametools sync qc_chem.tame --history          # 지금까지의 동기화 목록
tametools sync qc_chem.tame --json             # 다른 프로그램에서 읽을 수 있는 출력
tametools audit qc_chem.tame                   # 이력·데이터·설정 지문 검증
```

## sync 가 하는 일

1. `META[SYNC].SOURCE` 를 읽어 프로젝트의 열 이름에 맞춥니다(열 순서는 자유, 정의되지 않은 열은 읽지 않고 알림, 빈 행은 무시).
2. 프로젝트 DATA(지난번 스냅숏)와 비교해 **추가 / 수정 / 삭제**를 구분합니다. `KEY_IDS` 가 있으면 키로 맞추므로 엑셀을 정렬해도 변경이 아닙니다. 없으면 행 위치로 비교합니다(덧붙이기만 하는 로그용).
3. 추가는 그대로 받습니다. **이미 동기화한 행의 수정·삭제는 중단**하고 무엇이 어떻게 달라졌는지 보여 줍니다(종료 코드 1). 새 행만 골라 반영하지도 않습니다.
4. 전체 스냅숏에 `META[SYNC].WORK` 를 다시 실행합니다. 일부만 계산하지 않으므로 결과는 언제나 "지금 자료 전체의 결과"입니다.
5. 새 결과를 기존 결과 파일과 행 단위로 비교해 `NEW / CHANGED / SAME` 을 표시하고, 새 행과 바뀐 행(바뀐 열의 이전 → 현재 값)을 출력합니다.
6. 프로젝트를 먼저, 결과를 그다음에 교체합니다. 읽기·검증·분석 중 하나라도 실패하면 **아무 파일도 바뀌지 않습니다.**

그 밖에 확인하는 것:

- 프로젝트 설정(META)을 직접 고쳤는지 → `MANUAL_EDIT` 로 이력에 남기고 결과를 다시 계산합니다(기준값·규칙 변경으로 달라진 기존 결과가 `CHANGED` 로 보입니다).
- 프로젝트 DATA 나 결과 파일을 sync 밖에서 고쳤는지, 결과 파일이 없어졌는지 → 알리고 결과를 다시 만듭니다.
- tametools 구현(플러그인 포함)이 바뀌었는지 → 다시 계산해 결과가 같은지 확인합니다.

## `META[SYNC]`

| 항목 | 필수 | 뜻 |
|---|---|---|
| `SOURCE` | 예 | 원본 파일(프로젝트 파일 기준 상대 경로). `.xlsx` `.xlsm` `.csv` `.tsv` `.tame` |
| `SHEET` | 시트가 여럿이면 | 읽을 시트 이름 |
| `ENCODING` | 원본이 UTF-8 이 아닌 `.csv`/`.tsv` 이면 | 원본의 인코딩(예: `cp949`). 지정하지 않으면 UTF-8 만 읽고, 다른 인코딩은 추측하지 않고 멈춤 |
| `KEY_IDS` | 권장 | 한 행을 식별하는 열의 `COLUMN.ID` 목록 |
| `WORK` | 분석하려면 | 동기화마다 실행할 `META[WORKS]` 이름 |
| `RESULT` | 결과를 저장하려면 | 결과 파일(`.tame` 또는 `.xlsx`). 매번 같은 파일을 갱신 |
| `REPORT` | 아니오 | 보고서 파일(`.html`). 차트를 포함한 한 파일이며 매번 갱신. `RESULT` 가 있어야 함 |
| `RESULT_KEY` | 아니오 | 결과 행을 식별하는 열. 생략하면 플러그인이 선언한 `ROW_KEY`, 그것도 없으면 행 전체 내용 |
| `ON_CHANGE` | 아니오 | `STOP`(기본) 또는 `ACCEPT`(수정·삭제를 항상 인정) |

프로젝트 파일에서 직접 작성한 부분(설정과 주석)은 sync 가 글자 그대로 보존합니다.
파일 끝의 `[SYNC_STATE]`, `[[LOG]]`, `[PROVENANCE]` 는 sync 가 관리합니다.

## 결과 파일의 추적 열

| 열 | 뜻 |
|---|---|
| `sync_seq` | 이 결과 행이 처음 생긴 동기화 번호 |
| `synced_at` | 그 동기화 시각 |
| `sync_status` | 마지막 동기화 기준 `NEW` / `CHANGED` / `SAME` |

엑셀에서 `sync_status = NEW` 로 걸러 "이번에 추가된 결과"만 볼 수 있습니다.
결과를 엑셀로 받으려면 `RESULT = "qc_chem_result.xlsx"` 로 바꾸면 됩니다.

## 보고서 (`REPORT`)

`qc_chem_report.html` 은 외부 파일이나 추가 설치 없이 열리는 한 파일입니다(차트는 페이지 안에 들어 있고, 인쇄하면 PDF 로 남길 수 있습니다).

1. **이번 동기화**: 원본에 추가된 행, 새 결과와 그 판정, 이전 보고와 달라진 기존 결과(이전 → 현재)
2. **검사·수준별 현황**: 기준 평균±SD 와 관측 n·평균·SD·CV%, 평균 편차(SD 단위), 경고·거부 수, 최근 run 판정
3. **Levey-Jennings 관리도**: 관리물질(수준·lot·기준값)마다 1개. 평균과 ±1/2/3SD 선, 경고(▲)·거부(◆) 표식과 규칙 이름, 이번에 추가·변경된 점 표시
4. **경고·거부 목록과 조치 기록**: 걸린 규칙과 방식, 오차 유형, `qc-action` 으로 남긴 원인·조치(없으면 "조치 기록 없음")
5. **적용한 규칙과 기준값**: 검사별 규칙 표, 선언한 기준값
6. **동기화 이력**
7. **검토 기록**: `qc-review` 로 남긴 기간 검토(없으면 서명란)

```toml
[WESTGARD_QC.REPORT]
TITLE = "임상화학 일일 정도관리 보고서"
LAST_RUNS = 30        # 관리도와 통계에 표시할 최근 run 수 (기본 30)
```

보고서도 "전부 아니면 전무"에 포함됩니다. `--check` 나 중단된 동기화는 보고서를 바꾸지 않고, 보고서를 지우면 다음 sync 가 다시 만듭니다.

## 조치 기록과 검토 기록

거부된 run 에 대해 무엇을 확인하고 어떻게 조치했는지는 **프로젝트 파일에** 남깁니다.
원본 엑셀은 측정 데이터만 두고, 결과 파일과 보고서는 동기화마다 다시 만들어지기 때문입니다.

```sh
tametools qc-action qc_chem.tame --list                 # 조치 기록이 없는 거부 run, 지금까지의 기록
tametools qc-action qc_chem.tame --run 2026-11-01 --result Glucose \
    --cause "시약 lot 교체 후 상승" --action "재보정 후 관리물질 재측정" \
    --outcome "10:05 재측정 관리 내" --patient-impact "보고 전 발견, 재검 없음" --by "홍길동"
tametools qc-action qc_chem.tame --supersedes 1 --cause "..." --action "..." --by "홍길동"   # 기록 #1 정정
tametools qc-review qc_chem.tame --from 2026-10-01 --to 2026-10-31 --by "김책임"          # 기간 검토
tametools qc-review qc_chem.tame --list
```

| 항목 | 필수 | 뜻 |
|---|---|---|
| `--run` | 예 | 대상 run. 전체 값이나 앞부분(하루 1 run 이면 날짜만으로 충분) |
| `--result` | 아니오 | 검사 ID 또는 이름. 여러 개 가능. 생략하면 그 run 의 모든 검사 |
| `--cause`, `--action` | 예 | 원인과 조치 내용. 원인을 모르면 "원인 미상"처럼 적음 |
| `--outcome`, `--patient-impact` | 아니오 | 조치 후 결과, 환자 결과에 준 영향(보류·재검 여부) |
| `--by` | 예 | 기록자 |
| `--supersedes` | 아니오 | 정정할 기록 번호. 대상 run·검사는 그대로 이어받음 |

### 창으로 입력하기

옵션을 다 적는 대신 창(대화상자)에서 입력할 수 있습니다.

```sh
tametools qc-action qc_chem.tame --dialog                  # 조치 기록이 없는 거부 run 중에서 골라 기록
tametools qc-action qc_chem.tame --supersedes 1 --dialog   # 기록 #1 의 내용을 채운 창에서 고쳐 정정
tametools qc-review qc_chem.tame --dialog                  # 아직 검토하지 않은 기간을 채운 창
```

- **대상은 목록에서 고릅니다.** 조치 기록이 없는 거부 run 이 최근 것부터 나옵니다. 한 run 에서 여러 검사가 거부됐으면 "한 기록으로 함께"도 고를 수 있습니다.
  고를 것이 여러 개면 아무것도 미리 선택되어 있지 않습니다. 엉뚱한 run 에 기록되지 않게 하기 위해서입니다.
- **필수 항목이 비면 저장되지 않습니다.** 원인, 조치 내용, 기록자입니다. 기록자는 미리 채워 두지 않습니다.
- **명령에 적은 값은 채워진 채로 뜹니다.** 예: `--run 2026-11-01 --result Glucose --dialog`.
- **`--dialog` 없이도 뜹니다.** 터미널에서 직접 실행했는데 필수 항목이 빠져 있으면 창이 뜹니다. 스케줄러나 스크립트처럼 사람이 없는 실행에서는
  뜨지 않고 지금까지처럼 오류로 끝납니다. `--no-dialog` 는 어떤 경우에도 묻지 않습니다.
- **창을 띄울 수 없으면 터미널에서 묻습니다.** 화면이 없는 서버 등에서는 같은 항목을 글로 차례로 묻습니다. 환경 변수 `TAMETOOLS_DIALOG=terminal` 로 항상 글로 묻게 할 수 있습니다.
- **취소하면 아무것도 남지 않습니다.** 창에서 저장한 기록은 명령으로 남긴 기록과 똑같이 프로젝트 파일에 쌓입니다.

설치본(exe)에는 창을 띄우는 부품(Tcl/Tk)이 함께 들어 있습니다(빌드 설정 `packaging/windows/tametools.spec`).

- **고치지 않고 덧붙입니다.** 한 번 남긴 기록은 수정하지 않고, 정정은 이전 기록을 대체하는 새 기록으로 남습니다. 대체된 기록도 파일에 그대로 있습니다.
- **변조를 알 수 있습니다.** 기록은 앞 기록의 해시와 연결되고 실행 이력(LOG)에도 남습니다. 파일을 직접 고치면 다음 sync 와 보고서가 해당 기록 번호를 알려 줍니다.
- **보고서가 바로 갱신됩니다.** 기록을 남기면 원본을 다시 읽거나 재계산하지 않고 보고서만 다시 씁니다. 4절에 조치 내용이 붙고, 맨 위에 조치 기록이 없는 거부 run 수가 나옵니다.
- **sync 가 알려 줍니다.** 조치 기록이 없는 거부 run 이 있으면 sync 를 실행할 때마다 알림이 나옵니다. 동기화를 막지는 않습니다.
- **검토 기록**에는 기간, 검토자와 함께 그 시점의 run 수·거부 run 수·미조치 수가 남습니다. 보고서 기간 전체를 포함하는 검토 기록이 없으면 보고서에 서명란이 나옵니다.
- 기록을 남기려면 프로젝트가 마지막 동기화 상태여야 합니다. 설정을 직접 고쳤다면 먼저 sync 로 그 변경을 기록합니다.
- 결과 파일에는 조치 내용을 넣지 않습니다. 결과는 데이터와 설정만으로 다시 계산되는 값으로 두기 위해서입니다.

기록은 프로젝트 파일 끝의 `[[SYNC_RECORDS.ITEMS]]` 에 쌓이며 sync 가 관리하는 영역입니다.

## `WESTGARD_QC` 플러그인

선언한 기준값(평균·SD)에 대한 z 점수로 다중규칙을 적용합니다. 기준값은 자료에서 다시 추정하지 않습니다.

QC 기능 전체가 플러그인 패키지 하나(`tametools/src/tametools/plugins/westgard_qc/`)입니다. 규칙 계산, 보고서, 조치·검토 기록,
`qc-action`·`qc-review` 명령이 모두 그 안에 있고 tametools 의 공개 플러그인 API 만 씁니다. `tametools plugins` 의 끝줄
`plugin commands:` 에서 이 플러그인이 더한 명령을 볼 수 있습니다.

sync 프로젝트 없이 한 번만 계산해 화면으로 보려면 `--view` 를 씁니다. 관리도가 들어간 HTML 한 파일이 만들어지고,
조치·검토 기록에 관한 부분은 빠집니다(기록은 sync 프로젝트에서만 남기기 때문입니다).

```sh
tametools run-plugin qc_chem.tame WESTGARD_QC --view qc_view.html
```

| 규칙 | 뜻 | 구분 |
|---|---|---|
| `1_2s` | 1개가 ±2SD 초과 | 경고(기본) |
| `1_3s` | 1개가 ±3SD 초과 | 거부, 우연오차 |
| `2_2s` | 연속 2개가 같은 쪽 2SD 초과 | 거부, 계통오차 |
| `R_4s` | 한 run 안에서 +2SD 초과와 −2SD 초과가 함께 | 거부, 우연오차 |
| `4_1s` | 연속 4개가 같은 쪽 1SD 초과 | 거부, 계통오차 |
| `10x` | 연속 10개가 평균의 같은 쪽 | 거부, 계통오차 |

`RULES` / `WARNING_RULES` 에 `1_2.5s`, `3_1s`, `6x`, `8x`, `12x`, `2of3_2s` 같은 이름도 쓸 수 있습니다.

### 규칙을 하나씩, 검사마다 다르게 설정하기

설정은 세 단계이고 뒤의 것이 앞의 것을 덮어씁니다.

```toml
[WESTGARD_QC]
WARNING_RULES = ["1_2s"]                          # ① 모든 검사에 쓰는 기본 조합
RULES = ["1_3s", "2_2s", "R_4s", "4_1s", "10x"]

[WESTGARD_QC.RULE_SETTINGS."10x"]                 # ② 규칙 하나만 따로
ACTION = "WARNING"                                #    REJECT(거부) | WARNING(경고) | OFF(끔)
SCOPE = "WITHIN_MATERIAL"                         #    이 규칙만 같은 관리물질의 연속 run 으로 판정

[WESTGARD_QC.BY_RESULT.glucose]                   # ③ 검사 하나만 따로 (RESULT_ID 기준)
RULES = ["1_3s", "2_2s", "R_4s"]

[WESTGARD_QC.BY_RESULT.glucose.RULE_SETTINGS."2_2s"]
SCOPE = "ACROSS_MATERIAL"
```

| 설정 | 값 | 적용 대상 |
|---|---|---|
| `ACTION` | `REJECT` / `WARNING` / `OFF` | 모든 규칙 |
| `SCOPE` | `BOTH` / `WITHIN_MATERIAL` / `ACROSS_MATERIAL` | 연속 규칙(`2_2s`, `4_1s`, `10x`, `2of3_2s` 등). `1_2s`·`1_3s`(측정 1개)와 `R_4s`(한 run 안)는 범위가 정해져 있어 지정하면 오류 |
| 한계·개수 | 규칙 이름으로 지정 | `1_2.5s`, `3_1s`, `8x`, `12x`, `2of3_2s` 처럼 이름이 곧 설정 |
| `FORM` | `COUNT` / `RANGE` | `R_4s`. `COUNT`(기본): 하나는 +2SD 초과, 다른 하나는 −2SD 미만(원래 정의). `RANGE`: 최고값 − 최저값이 4SD 이상(일부 QC 소프트웨어 방식) |
| `TRIGGER` | `ALWAYS` / `1_2S` | 기본 조합 또는 검사별 |
| `AFTER_REJECT` | `RESTART` / `SKIP` / `CONTINUE` | 기본 조합 또는 검사별. 거부된 run 이후 연속 계수를 어떻게 할지 |

`AFTER_REJECT` 는 거부된 run 이 그 뒤의 연속 규칙(2_2s, 4_1s, 10x 등)에 주는 영향을 정합니다.

- `RESTART`(기본): 그 검사의 연속 계수를 모두 처음부터 다시 시작합니다. 거부 후 조치를 하고 다시 필요한 수만큼 모은다는 Westgard 의 설명을 따른 것입니다.
- `SKIP`: 거부된 run 의 값만 빼고 앞뒤 값을 이어서 셉니다(거부 행을 제외하는 QC 소프트웨어 방식).
- `CONTINUE`: 거부된 run 의 값도 계속 셉니다.

`RULES` 에 `1_2s` 를 적으면 경고가 아니라 거부 규칙이 됩니다. 실제로 각 검사에 적용된 조합은 결과 파일의
`META[PLUGIN].RULESETS` 와 보고서 5절의 표에 남습니다.

- "연속"은 두 가지로 봅니다. 같은 관리물질(수준·lot·기준값)의 연속 run(`across_run`), 그리고 한 run 안의 여러 수준(`within_run`) 또는 여러 수준을 합친 연속 run(`across_run_material`). `rule_scope` 열에 어느 쪽으로 걸렸는지 남습니다. `SCOPE` 로 한쪽만 쓸 수 있습니다.
- 결측 결과와 lot·기준값 변경은 연속을 끊습니다. 거부된 run 도 기본값(`AFTER_REJECT = "RESTART"`)에서는 연속을 끊습니다.
- 한계값과 정확히 같은 값은 벗어난 것으로 보지 않고(문헌의 "exceeds"), 평균과 정확히 같은 값은 `10x` 의 연속을 끊습니다. 이 두 가지는 문헌에 명시가 없어 이 도구가 정한 기준입니다.
- `TRIGGER = "1_2S"` 로 두면 고전적인 수기 방식처럼 그 run 에 ±2 SD 를 넘은 관리물질이 있을 때만 규칙을 봅니다(기본 `ALWAYS`).
  판단 기준은 측정값 자체입니다. `1_2s` 를 경고 목록에서 빼거나 거부 규칙으로 옮겨도 다른 규칙이 꺼지지 않습니다.
- 엑셀 날짜에는 시간대가 없으므로 `TIMEZONE = "Asia/Seoul"` 처럼 선언합니다. run 열이 없으면 측정일시가 같은 행들이 한 run 입니다.
- 출력: 측정 1건당 1행(`violation`, `warning`, `rule_scope`, `error_type`, `decision`, `run_decision`)과 run 요약 표.

각 행의 판정은 **그 run 과 그 이전 run 만** 사용합니다. 그래서 뒤에 run 이 추가되어도 앞선 run 의 판정은 바뀌지 않고,
바뀌었다면 원본 수정·설정 변경·같은 run 의 추가 측정 중 하나가 원인입니다.

판정은 관리 run 의 수동 검토를 돕는 규칙 출력이며, 결과 보고 허용 여부를 자동으로 결정하지 않습니다.

### 문헌과의 대응

| 항목 | 문헌 | 이 플러그인 |
|---|---|---|
| `1_2s` | 원래 절차에서는 경고. 거부 규칙으로 쓰면 정상 run 의 약 5%(N=1)·9%(N=2)·14%(N=3)를 잘못 거부 | 기본 경고. `RULES` 에 넣으면 거부 |
| `2_2s` | 한 run 의 여러 수준, 또는 같은 물질의 최근 2 run | 둘 다 판정(`within_run`, `across_run`) |
| `R_4s` | 한 run 안에서만. 원래는 +2SD/−2SD 를 세는 방식, 일부 소프트웨어는 차이 4SD 이상 | 한 run 안에서만. `FORM` 으로 두 방식 선택 |
| `4_1s`, `10x` | 한 물질의 4·10 run, 또는 2 수준 × 2·5 run. 어느 쪽인지 소프트웨어가 밝혀야 함 | 둘 다 판정하고 `rule_scope` 에 기록. 규칙별 `SCOPE` 로 선택 |
| 경고 없이 거부 규칙 적용 | 컴퓨터로 적용할 때는 1_2s 를 거치지 않고 모든 규칙을 동시에 적용 | `TRIGGER = "ALWAYS"`(기본). 수기 방식은 `1_2S` |
| 검사별 규칙 선택 | 시그마 수준에 따라 검사마다 다른 조합(예: 6σ 는 1_3s 만, 4σ 미만은 8x 추가) | `BY_RESULT` 로 검사별 지정. 시그마 계산과 run 당 관리물질 수(N) 설계는 하지 않음 |
| 3 수준 관리 | `2of3_2s`, `3_1s`, `6x`/`9x`/`12x` | 규칙 이름으로 지원 |
| `7T`(추세) | Westgard 규칙 조합에 포함되지 않음(일부 소프트웨어만 제공) | 지원하지 않음 |
| 거부된 run 이후 | 다시 세기 시작(Westgard) 또는 거부 행 제외(소프트웨어) | `AFTER_REJECT`: `RESTART`(기본)/`SKIP`/`CONTINUE` |
| 관측 평균·SD | 거부된 run 의 값은 제외(Westgard). 제외하지 말라는 견해도 있음 | 보고서 통계는 제외하고 제외 수를 표시 |
| 기준 평균·SD | 검사실 자체 자료로 설정(20회 이상, 여러 날). 제조사 범위는 너무 넓음 | 선언값만 사용. 보고서가 관측 SD 와의 비를 보여 주고 크게 다르면 알림 |

출처: Westgard QC(westgard.com)의 multirule·Sigma Rules·QC 기초 강의, Bio-Rad Unity Real Time 도움말, Badrick(2008).
CLSI C24 원문과 1981년 원 문헌은 이 표의 근거로 쓰지 않았습니다.

## 알아둘 점

- 엑셀에서 저장하지 않은 변경은 읽히지 않습니다. 결과 파일을 엑셀로 열어 둔 채 실행하면 시작 전에 알리고 멈춥니다.
- 수식 셀은 엑셀이 마지막으로 계산해 저장한 값을 읽습니다.
- 동기화 1회마다 프로젝트 파일이 2~3 KB 늘어납니다(LOG 1건 + 이력 1줄 + 추가된 행). 설정 스냅숏은 설정이 바뀔 때만 추가됩니다.
- 한 프로젝트를 두 사람이 동시에 sync 하는 경우는 다루지 않습니다.
